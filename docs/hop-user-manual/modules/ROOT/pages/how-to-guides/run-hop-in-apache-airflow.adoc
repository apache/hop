= image:how-to-guides/run-hop-in-apache-airflow/airflow-logo.svg[Apache Airflow, width="75vw", align="center"]Run workflows and pipelines in Apache Airflow

This is the Airflow-specific how-to.
For cron, systemd, Jenkins, a Kubernetes CronJob and the hop-run contract they all share, see xref:how-to-guides/scheduling-workflows-and-pipelines.adoc[Scheduling workflows and pipelines].

The examples on this page are written for and tested with Apache Airflow 3.4.0 and Apache Hop 2.20.0.

To go the other way and start an Airflow DAG from a Hop workflow, use the xref:workflow/actions/airflow-trigger-dag-run.adoc[Trigger Airflow DAG run] action.

This page writes a DAG in Python that runs a whole workflow or pipeline in one task.
Since Hop 2.21, Airflow can also run the workflows of a project without a DAG file, with one Airflow task per action: see xref:hop-tools/hop-airflow-bundle.adoc[hop airflow-bundle] and the xref:workflow/workflow-run-configurations/airflow-workflow-engine.adoc[Apache Airflow workflow engine].

== What is Apache Airflow?

From the https://airflow.apache.org/[Apache Airflow website]:

[quote]
Airflow is a platform created by the community to programmatically author, schedule and monitor workflows.

Airflow runs Directed Acyclic Graphs, or https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/dags.html[DAGs^]. A DAG is a collection of tasks, organized in a way that reflects their relationships and dependencies.

A DAG is defined in a Python script, which represents the DAG's structure (tasks and their dependencies) as code.

From an Apache Hop point of view, our focus is different: Apache Hop wants to enable citizen developers to be productive data engineers without the need to write code. With that in mind, we only use a small part of what Apache Airflow can do: Airflow starts a Hop container, Hop runs the workflow or pipeline.

== Run Apache Airflow in Docker Compose

The goal of this page is to get a basic Airflow setup running to show how Apache Airflow and Apache Hop work together. Check out the https://airflow.apache.org/docs/apache-airflow/stable/installation/index.html[installation options^] if you want to build a production-ready Apache Airflow installation.

We use Docker Compose to get Apache Airflow up and running in a couple of minutes.

Apache Airflow provides a https://airflow.apache.org/docs/apache-airflow/3.4.0/docker-compose.yaml[docker-compose.yaml^] file (see https://airflow.apache.org/docs/apache-airflow/stable/howto/docker-compose/index.html[Running Airflow in Docker^]).
The https://github.com/apache/hop/blob/main/docs/hop-user-manual/modules/ROOT/assets/files/how-to-guides/apache-airflow/docker-compose.yaml[docker-compose.yaml^] file in the Hop repository is that file with these changes:

* **AIRFLOW\__CORE__LOAD_EXAMPLES** is "false": we don't need the Airflow sample DAGs.
* The `airflow-worker` service, which runs the tasks, mounts the Docker socket **/var/run/docker.sock**, so the DockerOperator can start `apache/hop` containers.
* The `airflow-worker` service is added to the group in **DOCKER_GID**, so it is allowed to use the Docker socket.

WARNING: Mounting the Docker socket gives the Airflow worker, and every DAG it runs, root-equivalent access to the Docker host. Only do this on a machine you use for testing. On a shared or production platform, use the <<kubernetes,KubernetesPodOperator>> instead.

Save the file in an empty folder.
Airflow needs an `.env` file next to it.
On Linux, put your user id and the group id of the Docker socket in it, so the files Airflow creates are yours and the worker can use the Docker socket:

[source, bash]
----
mkdir -p ./dags ./logs ./plugins ./config
echo "AIRFLOW_UID=$(id -u)" > .env
echo "DOCKER_GID=$(getent group docker | cut -d: -f3)" >> .env
----

On macOS and Windows (Docker Desktop), an `.env` file with `AIRFLOW_UID=50000` is enough.

To run Apache Airflow, go to the folder where you saved the file and run

[source, bash]
----
docker compose up -d
----

The first start takes a couple of minutes: `airflow-init` creates the database and the user, then the other services start.
`docker compose ps` shows all services as `healthy` when Airflow is ready.

Go to http://localhost:8080 in your browser and log in with username "airflow" and password "airflow".

To use another username and password, set the **_AIRFLOW_WWW_USER_USERNAME** and **_AIRFLOW_WWW_USER_PASSWORD** variables in the `.env` file, or use any of the other ways to https://docs.docker.com/compose/how-tos/environment-variables/set-environment-variables/[set variables^] in Docker Compose.

After you log in, Apache Airflow shows an empty list of DAGs.

image:how-to-guides/run-hop-in-apache-airflow/apache-airflow-empty-server.png[Apache Airflow - Empty server, width="75%"]

== Your first Apache Airflow and Apache Hop DAG

NOTE: This page runs a *short-lived* `apache/hop` container with a local engine.
That is often what you want: if the project is already in the image, you do not need a Hop Server at all.
Send xref:metadata-types/execution-information-location.adoc[execution information] to a volume, database, OpenSearch, Neo4j or Elastic so you can inspect the run after the container exits.
See xref:hop-server/deploy-project-image.adoc#skip_hop_server_short_lived_containers[Skip Hop Server: short-lived containers].
To have Airflow submit work to a running Hop Server instead (remote run configuration, export resources), see xref:hop-server/deploy-export-resources.adoc[Remote run with export resources].

We'll use the Apache Airflow https://airflow.apache.org/docs/apache-airflow-providers-docker/stable/_api/airflow/providers/docker/operators/docker/index.html[DockerOperator^] to run Apache Hop workflows and pipelines in a container.

You don't need to be an Apache Airflow, Docker, or Python expert to create DAGs: we'll treat DAGs as just another text file.
Since we use a container to run our workflows and pipelines, the configuration in our DAG looks very similar to the environment variables you pass to the xref:docker-container.adoc[short-lived Apache Hop container].

The examples use the `samples` project that comes with Apache Hop: the `config/projects/samples` folder in your Hop installation.

Import the DockerOperator and the `Mount` type in your DAG:

[source, python]
----
from airflow.providers.docker.operators.docker import DockerOperator
from docker.types import Mount
----

Let's take a look at the end of the Apache Hop task first:

[source, python]
----
mounts=[
    Mount(source="LOCAL_PATH_TO_PROJECT_FOLDER", target="/project", type="bind"),
],
----

The mounts section is where we link your project folder to the container.
**LOCAL_PATH_TO_PROJECT_FOLDER** is the absolute path to the project folder (the folder with your `project-config.json` file, `metadata` folder, workflows and pipelines). This folder is mounted as `/project` inside the container.

The Hop container is started by the Docker daemon on the host, not inside the Airflow worker, so this is a path on the Docker host, not a path in the Airflow container.

Define and configure the pipeline in your DAG task:

[source, python]
----
hop = DockerOperator(
    task_id="sample-pipeline",
    image="apache/hop:2.20.0",
    environment={
        "HOP_LOG_LEVEL": "Basic",
        "HOP_FILE_PATH": "${PROJECT_HOME}/transforms/null-if-basic.hpl",
        "HOP_PROJECT_FOLDER": "/project",
        "HOP_PROJECT_NAME": "hop-airflow-sample",
        "HOP_RUN_CONFIG": "local",
    },
----

The parameters to specify here are:

* **task_id**: a unique id for this Airflow task in the DAG
* **image**: the Apache Hop image to use. Pin a release, e.g. "apache/hop:2.20.0". "apache/hop:latest" changes with every release, and "apache/hop:Development" is the latest development build.
* **environment** tells the container which pipeline to run and how. These are the same environment variables you pass to a short-lived container without Airflow:
** HOP_LOG_LEVEL: the logging level to use with your workflow or pipeline
** HOP_FILE_PATH: the path to the workflow or pipeline you want to run. `${PROJECT_HOME}` is the project folder in the container.
** HOP_PROJECT_FOLDER: the folder where your project files live. In this example, this is the `/project` folder we mounted in the previous section.
** HOP_PROJECT_NAME: your Apache Hop project's name. This is only used in the container (and shows in the logs). It does not have to be the name you use in Hop Gui, but keeping things consistent never hurts.
** HOP_RUN_CONFIG: the workflow or pipeline run configuration to use. In most cases, this is a local run configuration.

The xref:docker-container.adoc[Docker container] page lists all the variables.

That's everything we need for a first run. The full DAG looks like this:

[source, python]
----
from datetime import datetime

from airflow.providers.docker.operators.docker import DockerOperator
from airflow.providers.standard.operators.empty import EmptyOperator
from airflow.sdk import DAG
from docker.types import Mount

with DAG(
    dag_id="sample-pipeline",
    start_date=datetime(2026, 1, 1),
    schedule=None,
    catchup=False,
    is_paused_upon_creation=False,
) as dag:
    start_dag = EmptyOperator(task_id="start_dag")
    end_dag = EmptyOperator(task_id="end_dag")
    hop = DockerOperator(
        task_id="sample-pipeline",
        image="apache/hop:2.20.0",
        environment={
            "HOP_LOG_LEVEL": "Basic",
            "HOP_FILE_PATH": "${PROJECT_HOME}/transforms/null-if-basic.hpl",
            "HOP_PROJECT_FOLDER": "/project",
            "HOP_PROJECT_NAME": "hop-airflow-sample",
            "HOP_RUN_CONFIG": "local",
        },
        docker_url="unix://var/run/docker.sock",
        network_mode="bridge",
        mounts=[
            Mount(source="LOCAL_PATH_TO_PROJECT_FOLDER", target="/project", type="bind"),
        ],
        mount_tmp_dir=False,
        auto_remove="success",
    )
    start_dag >> hop >> end_dag
----

`mount_tmp_dir=False` stops the DockerOperator from mounting a temporary folder of the worker into the Hop container. That folder does not exist on the Docker host.
`auto_remove="success"` removes the Hop container when the run succeeds and keeps it when it fails, so you can still check it with `docker logs`.

== Deploy and run your first DAG

To deploy your DAG, put it in Airflow's `dags` folder: the `dags` folder next to the `docker-compose.yaml` file.
Airflow checks this folder for new DAG files every five minutes by default.

Save the DAG we just created in your dags folder as `apache-hop-dag-simple.py`. After a short wait, your DAG shows up in the list of DAGs.

If there are any syntax errors in your DAG, Airflow shows a red import error badge next to the number of DAGs. Click it for the details, as shown in the image below.

image:how-to-guides/run-hop-in-apache-airflow/apache-airflow-dag-error.png[Apache Airflow - DAG error, width="60%"]

NOTE: If the Hop container needs to reach a database or service on your host machine, use `host.docker.internal` as the host name in the Hop connection. On Linux, also add `extra_hosts={"host.docker.internal": "host-gateway"}` to the DockerOperator.

If your DAG is deployed correctly, it shows up in the list of DAGs.

image:how-to-guides/run-hop-in-apache-airflow/apache-airflow-dag-available.png[Apache Airflow - DAG available, width="75%"]

Click the **sample-pipeline** DAG to see more details about it. The "Code" tab shows the DAG you just deployed. The graph button at the top of the left panel shows the graph of the DAG. This graph is very simple, which is intentional.

== Using variables and parameters in a DAG

Your real-life pipelines will be more complex than the very simple example pipeline we just ran.
You'll want to use variables from your environment configuration files, and pass parameters to your pipelines and workflows.

Save the environment configuration file below as `hop-airflow-config.json` in a config folder next to your project folder.
We'll use the pipeline `pipelines/pipeline-with-parameter.hpl` from the samples project to print a pipeline parameter and a variable from the environment configuration file to the logs.

[source, json]
----
{
  "variables" : [ {
    "name" : "ENV_VARIABLE",
    "value" : "variable value",
    "description" : ""
  } ]
}
----

This pipeline accepts a parameter `PRM_EXAMPLE` and writes it and the `ENV_VARIABLE` variable to the logs:

image:how-to-guides/run-hop-in-apache-airflow/apache-airflow-pipeline-with-parameter.png[Apache Airflow - run a pipeline with parameters, width="75%"]

We'll create a new DAG for this example. Most of it is the same as the previous example.

First, declare the parameter in the DAG with `params`.
Airflow shows it as a field in the trigger form and uses the default value for scheduled runs.

[source, python]
----
params={"prm_example": Param("default value", type="string")},
----

Then pass the value to the pipeline.
The `environment` of the DockerOperator is a template, so `{{ params.prm_example }}` is replaced with the value of the run.
`HOP_RUN_PARAMETERS` is a comma-separated list of `NAME=value` pairs, so the value can't contain a comma.

We also add the environment: `HOP_ENVIRONMENT_NAME` is the name of the environment the container creates, `HOP_ENVIRONMENT_CONFIG_FILE_NAME_PATHS` is the path of the environment configuration file in the container.

[source, python]
----
environment={
    "HOP_RUN_PARAMETERS": "PRM_EXAMPLE={{ params.prm_example }}",
    "HOP_LOG_LEVEL": "Basic",
    "HOP_FILE_PATH": "${PROJECT_HOME}/pipelines/pipeline-with-parameter.hpl",
    "HOP_PROJECT_FOLDER": "/project",
    "HOP_PROJECT_NAME": "hop-airflow-sample",
    "HOP_ENVIRONMENT_NAME": "hop-airflow-sample-env",
    "HOP_ENVIRONMENT_CONFIG_FILE_NAME_PATHS": "/project-config/hop-airflow-config.json",
    "HOP_RUN_CONFIG": "local",
},
----

The environment configuration file has to be in the container, so mount the config folder as `/project-config`:

[source, python]
----
mounts=[
    Mount(source="LOCAL_PATH_TO_PROJECT_FOLDER", target="/project", type="bind"),
    Mount(source="LOCAL_PATH_TO_CONFIG_FOLDER", target="/project-config", type="bind"),
],
----

The full DAG:

[source, python]
----
from datetime import datetime

from airflow.providers.docker.operators.docker import DockerOperator
from airflow.providers.standard.operators.empty import EmptyOperator
from airflow.sdk import DAG, Param
from docker.types import Mount

with DAG(
    dag_id="pipeline-with-parameter",
    start_date=datetime(2026, 1, 1),
    schedule=None,
    catchup=False,
    is_paused_upon_creation=False,
    params={"prm_example": Param("default value", type="string")},
) as dag:
    start_dag = EmptyOperator(task_id="start_dag")
    end_dag = EmptyOperator(task_id="end_dag")
    hop = DockerOperator(
        task_id="pipeline-with-parameter",
        image="apache/hop:2.20.0",
        environment={
            "HOP_RUN_PARAMETERS": "PRM_EXAMPLE={{ params.prm_example }}",
            "HOP_LOG_LEVEL": "Basic",
            "HOP_FILE_PATH": "${PROJECT_HOME}/pipelines/pipeline-with-parameter.hpl",
            "HOP_PROJECT_FOLDER": "/project",
            "HOP_PROJECT_NAME": "hop-airflow-sample",
            "HOP_ENVIRONMENT_NAME": "hop-airflow-sample-env",
            "HOP_ENVIRONMENT_CONFIG_FILE_NAME_PATHS": "/project-config/hop-airflow-config.json",
            "HOP_RUN_CONFIG": "local",
        },
        docker_url="unix://var/run/docker.sock",
        network_mode="bridge",
        mounts=[
            Mount(source="LOCAL_PATH_TO_PROJECT_FOLDER", target="/project", type="bind"),
            Mount(source="LOCAL_PATH_TO_CONFIG_FOLDER", target="/project-config", type="bind"),
        ],
        mount_tmp_dir=False,
        auto_remove="success",
    )
    start_dag >> hop >> end_dag
----

Save it in your dags folder as `apache-hop-dag-with-parameter.py` and wait for it to appear in the list of DAGs.

image:how-to-guides/run-hop-in-apache-airflow/apache-airflow-two-dags.png[Apache Airflow - two DAGs, width="75%"]

Click the play icon of the **pipeline-with-parameter** DAG. The trigger form now has a **prm_example** field. Enter a value and click **Trigger**.

image:how-to-guides/run-hop-in-apache-airflow/apache-airflow-trigger-dag-with-config.png[Apache Airflow - trigger DAG with a parameter, width="60%"]

You can also trigger the DAG from the command line, with the value in the run configuration:

[source, bash]
----
docker compose exec airflow-scheduler \
  airflow dags trigger pipeline-with-parameter -c '{"prm_example": "hello from airflow"}'
----

== Run Hop on Kubernetes with the KubernetesPodOperator

Managed Airflow services such as Amazon MWAA, Google Cloud Composer and Astronomer do not give you a Docker socket, so the DockerOperator doesn't work there.
Use the https://airflow.apache.org/docs/apache-airflow-providers-cncf-kubernetes/stable/operators.html[KubernetesPodOperator^] instead: it runs the same `apache/hop` image as a pod in a Kubernetes cluster.
It is in the `apache-airflow-providers-cncf-kubernetes` package, which the official Airflow image already contains.

A pod can't mount a folder from your machine. Put the project in an image (see xref:hop-server/deploy-project-image.adoc[Project in a Docker image]) and the environment configuration file in a ConfigMap:

[source, bash]
----
kubectl create configmap hop-airflow-config --from-file=hop-airflow-config.json
----

The DAG below runs the pipeline with parameter from the previous section in a pod.
`registry.example.com/your-project:1.0` is your project image, with the project in `/your-project`.

[source, python]
----
from datetime import datetime

from airflow.providers.cncf.kubernetes.operators.pod import KubernetesPodOperator
from airflow.sdk import DAG, Param
from kubernetes.client import models as k8s

with DAG(
    dag_id="pipeline-with-parameter-k8s",
    start_date=datetime(2026, 1, 1),
    schedule=None,
    catchup=False,
    is_paused_upon_creation=False,
    params={"prm_example": Param("default value", type="string")},
) as dag:
    hop = KubernetesPodOperator(
        task_id="pipeline-with-parameter",
        name="hop-pipeline-with-parameter",
        namespace="default",
        image="registry.example.com/your-project:1.0",
        env_vars={
            "HOP_RUN_PARAMETERS": "PRM_EXAMPLE={{ params.prm_example }}",
            "HOP_LOG_LEVEL": "Basic",
            "HOP_FILE_PATH": "${PROJECT_HOME}/pipelines/pipeline-with-parameter.hpl",
            "HOP_PROJECT_FOLDER": "/your-project",
            "HOP_PROJECT_NAME": "hop-airflow-sample",
            "HOP_ENVIRONMENT_NAME": "hop-airflow-sample-env",
            "HOP_ENVIRONMENT_CONFIG_FILE_NAME_PATHS": "/project-config/hop-airflow-config.json",
            "HOP_RUN_CONFIG": "local",
        },
        volumes=[
            k8s.V1Volume(
                name="hop-config",
                config_map=k8s.V1ConfigMapVolumeSource(name="hop-airflow-config"),
            )
        ],
        volume_mounts=[
            k8s.V1VolumeMount(name="hop-config", mount_path="/project-config", read_only=True)
        ],
        get_logs=True,
        on_finish_action="delete_succeeded_pod",
    )
----

`get_logs=True` copies the Hop output to the task log.
`on_finish_action="delete_succeeded_pod"` keeps a failed pod, so you can check it with `kubectl logs`.

How Airflow connects to the cluster depends on where it runs.
On Cloud Composer and Astronomer, the default connection runs the pod in the Airflow cluster itself.
On MWAA, and on your own Airflow outside the cluster, set `kubernetes_conn_id` or `config_file` to point the operator at your cluster.
See the KubernetesPodOperator documentation and the documentation of your platform.

== Scheduling a DAG in Apache Airflow

So far, we've triggered DAGs manually. There are lots of https://airflow.apache.org/docs/apache-airflow/stable/authoring-and-scheduling/index.html[well-documented^] options to schedule DAGs in Apache Airflow. Since scheduling your DAGs is not really Apache Hop related, we'll only cover this briefly here.

For the same hop-run / short-lived-container contract with cron, systemd, Jenkins or a Kubernetes CronJob, see xref:how-to-guides/scheduling-workflows-and-pipelines.adoc[Scheduling workflows and pipelines].

One option is a cron expression. For example, to run a DAG at 10:00 every morning, change `schedule` from `None` to a cron expression in the `with DAG` line of your DAG:

[source, python]
----
with DAG(
    dag_id="sample-pipeline",
    start_date=datetime(2026, 1, 1),
    schedule="0 10 * * *",
    catchup=False,
    is_paused_upon_creation=False,
) as dag:
----

Scheduled runs use the default values of the DAG's `params`.
See https://airflow.apache.org/docs/apache-airflow/stable/authoring-and-scheduling/cron.html[Cron & Time Intervals^] in the Airflow documentation for cron expressions, presets such as `@daily`, and other ways to schedule a DAG.

== Summary

We've covered the basics of running Apache Hop pipelines (or workflows) in Apache Airflow with the DockerOperator and the KubernetesPodOperator.

There are other options:

* xref:hop-tools/hop-airflow-bundle.adoc[hop airflow-bundle] turns every workflow of a project into a DAG with one task per action, and the xref:workflow/workflow-run-configurations/airflow-workflow-engine.adoc[Apache Airflow workflow engine] runs and follows such a DAG from Hop GUI (Hop 2.21 and later).
* Airflow's https://airflow.apache.org/docs/apache-airflow-providers-standard/stable/operators/bash.html[BashOperator^] runs xref:hop-run/index.adoc[hop-run] directly, if Hop is installed on the Airflow workers.
* The https://airflow.apache.org/docs/apache-airflow-providers-http/stable/operators.html[HTTP operator^] runs pipelines or workflows on a remote xref:hop-server/index.adoc[Hop Server], for example through its xref:hop-server/web-service.adoc[web services] or xref:hop-server/json-api.adoc[JSON API].
Hop Server requires authentication: store the Hop Server user and password in the Airflow HTTP connection.
Since Hop 2.20, this includes the JSON API.

Airflow is one scheduler among several.
