= Native Spark Pipeline Engine

== Overview

The native Spark pipeline engine executes batch Hop pipelines on *Apache Spark 4.1.x* without Apache Beam.
It builds a Spark SQL Dataset graph from the pipeline and runs transforms via native Dataset operators or generic `mapPartitions` mini-pipelines.

For a full introduction — concepts, `+local[*]+`, fat jar, `spark-submit`, Spark File I/O, `${Internal.Transform.ID}`, metrics, limitations, and integration-test examples — see
xref:pipeline/spark/getting-started-with-native-spark.adoc[Getting started with the native Spark pipeline engine].

Paths on *Spark File* and *Lake Table* transforms are **Spark/Hadoop URIs**, not Hop VFS schemes — see
xref:pipeline/spark/paths-and-filesystems.adoc[Paths and file systems on native Spark].

This page is *not* the same as xref:pipeline/pipeline-run-configurations/beam-spark-pipeline-engine.adoc[Beam Spark], which runs Hop over the Apache Beam Spark runner (Spark 3.5.x line).

image::pipeline/spark/native-spark-pipeline-engine-run-configurtion-editor.png[Native Spark pipeline run configuration editor,width=70%]

=== Requirements

* Java {java-version}
* Spark 4.1.x (bundled under `plugins/engines/spark/lib` for `+local[*]+`)

=== Options

The options are on five tabs: *General*, *Cluster*, *Resources*, *Spark settings* and *Hop on Spark*.
The dialog shows only the options that do something for the cluster type and deploy mode: a local run, for example, has no fat jar, staging or executor settings.

==== Load configuration template

Use **Load configuration template** to fill the fields below from a common deployment style:

* *Local execution* — `+local[*]+`, Spark UI off (embedded Spark in Hop)
* *Local (capped cores)* — `local[4]`
* *Spark standalone server* — `spark://host:7077` (replace host), sample driver/executor memory. Leave *Fat jar file location* empty: Hop builds the fat jar for the executors. See xref:pipeline/spark/local-standalone-cluster.adoc[Local standalone cluster].
* *spark-submit (cluster)* — cluster type *spark-submit*: the master stays empty so `spark-submit --master` wins; use a `native-provided` fat jar. Hop GUI, `hop-run` and Hop Server refuse to run a pipeline with it, see <<submitted>>.
* *Databricks* — cluster type *Databricks*: Hop runs the pipeline as a job on a Databricks cluster. Then choose the Databricks connection, the compute and a volume folder on the *Cluster* tab. See xref:pipeline/spark/databricks.adoc[Native Spark on Databricks].
* *YARN client* — master `yarn`, and `spark.submit.deployMode=client` in the Spark settings. Also set *Hadoop configuration folder* (or `HADOOP_CONF_DIR`). See xref:pipeline/spark/yarn.adoc[Run native Spark pipelines on YARN].
* *Lakehouse local* — same as local; Delta/Iceberg connectors live on the plugin classpath

A template sets the cluster type, the Spark master, the application name, the fat jar, the Spark settings and the memory and cores; the other options stay as they are. It asks for confirmation when the form already has custom values. The form fields update immediately after you apply a template. Edit values afterward as needed.

==== Test configuration

*Test configuration* checks the run configuration from the Hop machine and lists what it found, with a fix for every check that does not pass.
Nothing is submitted to the cluster.
*Test with a test job* runs the same checks, and then a small pipeline on the cluster: it uses the cluster for a moment, and finds what the checks can't see, such as the Java version of the executors or a class conflict in the fat jar.
The checks follow the cluster type and deploy mode; a check whose prerequisite failed is skipped.

==== Names in the Spark UI

The Spark jobs, stages and SQL queries of a run carry the name of the pipeline and of the transform that starts them, in the Spark UI and on Databricks: every job of a run is in the job group `hop-<run id>`, its description is `Hop pipeline '<pipeline>', transform '<transform>' (<plugin id>)` and its stages are named `Hop <pipeline> → <transform>`. Spark runs the transforms between two shuffles in one stage, which carries the name of the transform whose output started it, usually an output transform.

[[fat-jar-on-executors]]
==== The fat jar on the executors

The executors need Hop's classes: the fat jar of the Hop installation, about 600 MB, which Hop builds once and keeps until the installation changes. How it reaches them:

* *No staging folder, client mode*: every executor downloads the fat jar from Hop at the start of every run, and on a standalone cluster each executor keeps its copy in the worker's work folder. Spark keeps those folders until `spark.worker.cleanup.enabled` is set on the workers, so a busy cluster fills its disks.
* *Staging folder*: Hop uploads the fat jar once (the file is named after its content) and the executors download it from there.
* *Staging folder that every worker mounts, with a `local:` URL for the cluster*: Spark uses the fat jar where it is, without a download or a copy. This is the fastest way to start a run.

[[cluster-mode]]
==== Cluster mode

In client mode, the Hop process is the Spark driver: it has to stay running and reachable by the executors for the whole run. In cluster mode Hop hands the run to the cluster:

. Hop builds the fat jar (or reuses its cached one) and exports the project: the definitions, the metadata and the variables of the run.
. It uploads both to the *Staging folder*, unless a file with the same name and size is already there.
. It submits `MainSpark` to the REST submission server of the Spark master. The driver starts on a worker, loads the project package and runs the pipeline with the same run configuration.
. Hop follows the driver until it ends. The pipeline fails when the driver fails; *Stop* kills the driver.

Requirements:

* A cluster Hop can submit to:
** a Spark standalone master (`spark://host:port`) with the REST submission server enabled: `spark.master.rest.enabled=true`, for example `SPARK_MASTER_OPTS=-Dspark.master.rest.enabled=true` in `spark-env.sh`; or
** YARN (master `yarn`), with the *Hadoop configuration folder* (or `HADOOP_CONF_DIR`) set. Hop submits with Spark's own YARN client inside the Hop process, so no Spark installation is needed, and follows and kills the application through the ResourceManager. See xref:pipeline/spark/yarn.adoc#cluster-mode[YARN cluster mode].
** Kubernetes (master `k8s://https://<api server>`), see <<kubernetes>>; or
** Databricks (cluster type *Databricks*), see <<databricks>>.
* A project: the driver on the cluster finds the pipeline in the project package. A driver on a host that has the project folder at the same path, a shared file system for example, uses that folder instead, but only when it holds the same project files as the package.
* Data on storage the workers read: a path under `${PROJECT_HOME}` points into the package copy on the cluster. Use a variable such as `HOP_DATA` for data paths.

[IMPORTANT]
====
Treat the staging folder like the project itself. The project package holds the project's metadata, with the connection passwords encoded the way Hop stores them, and the variables of the run, encoded the same way. That is every variable of the run, as for a run on a Hop Server: the project, environment and parameter values, and the system properties of the Hop process (`-D` options and `hop-config.json` variables), without those of Java itself. A package stays in the staging folder until the cleanup removes it (<<staging-cleanup>>). Hop's default encoding can be reversed by anyone who can read the files, so only the people and the Spark cluster that run your pipelines should be able to read the staging folder. With a stronger password encoder (`HOP_PASSWORD_ENCODER_PLUGIN`), the cluster driver needs the same encoder and key.
====

The driver log is on the worker that ran it: the Spark master UI lists it under *Completed Drivers*. Per-transform metrics of a cluster-mode run are not shown in Hop yet.

[[staging-cleanup]]
===== Cleaning up the staging folder

Every staged file is named after its content. A new Hop version, an installed or removed plugin, or a changed project stages new files next to the old ones, and a fat jar is several hundred MB. Clients with different Hop versions or plugins can share one staging folder: they never overwrite each other's files.

Whether a file is still needed can only be told from its use. Each run writes a small marker next to every file it uses, `<file>.lastused`, also when the file was already staged, and refreshes it every hour while the driver runs. A file whose marker is older than the retention is removed together with its sidecars (`.sha256`, `.lastused`):

* Automatically: after a cluster-mode submission, at most once a day per Hop installation and staging folder. The retention is `HOP_STAGING_RETENTION_DAYS` (variable, system property or environment variable), 14 days by default; `0` turns the automatic cleanup off.
* On request: *Tools* > *Clean up a cluster staging folder...* in Hop GUI lists the staged files with their size, last use and state, and removes the unused ones. From the command line: `hop-conf --staging-list=<folder>` and `hop-conf --staging-cleanup=<folder>`, see xref:hop-tools/hop-conf/hop-conf.adoc[hop-conf].

Only the files Hop stages are considered (`hop-native-<hash>.jar`, `hop-spark-package-<hash>.zip`, `spark-runtime-<hash>.zip`); anything else in the folder stays. A file marked by a newer Hop version in a format this version does not know is kept, and so is a file whose last use the folder can't tell (a store that reports no modification time and no readable marker). A file without a `.lastused` marker is kept too: an older Hop version staged it without one, for example the fat jar of a Databricks job it deployed, and that job may still use it. Remove such a file by hand once nothing uses it. Each file is checked again just before it is removed, so a run that starts using it meanwhile keeps it.

A file with a `<file>.keep` sidecar is never removed. The xref:workflow/actions/databricks-job-run.adoc[Databricks job run] action writes one next to the fat jar of every job it deploys: the job uses the jar on its own schedule, without a Hop run to mark it. Delete the `.keep` file once no job uses the jar any more.

Keep the retention longer than any run lasts without Hop following it, and do not let a bucket lifecycle rule expire the staging folder: such a rule goes by upload time and would remove a fat jar that is used every day.

[[databricks]]
==== Running on Databricks

With the cluster type *Databricks*, a pipeline that Hop GUI, `hop-run` or Hop Server runs goes to a Databricks cluster:

. Hop builds the fat jar (or reuses its cached one) and exports the project, as in cluster mode.
. It uploads both to the *Staging folder*, a Unity Catalog volume folder such as `/Volumes/main/default/hop/staging`, through the Databricks Files API.
. It submits a one-time job run of `MainSpark` (`runs/submit`) on the *Databricks compute*, with the fat jar as its library. The run loads the project package and runs the pipeline with the same run configuration.
. Hop follows the run until it ends and logs the link to its page in Databricks. The pipeline fails when the run fails; *Stop* cancels the run.

The run configuration needs no Spark master, deploy mode or executor sizes: Databricks sets them from the cluster. The same run configuration works for the jobs that the xref:workflow/actions/databricks-job-run.adoc[Databricks job run] action deploys: when Databricks starts `MainSpark`, the pipeline runs on the job's cluster, it is not submitted again. The staged files are marked and cleaned up as in cluster mode (<<staging-cleanup>>). How to set up the workspace, the token and the volume: xref:pipeline/spark/databricks.adoc[Native Spark on Databricks].

[[submitted]]
==== spark-submit

The cluster type *spark-submit* is for pipelines that you start yourself with `spark-submit` and `MainSpark`, for example on YARN, a standalone cluster, Amazon EMR or Google Dataproc: `spark-submit` sets the master. When Hop GUI, `hop-run` or Hop Server runs a pipeline with this cluster type, Hop refuses with an error: without a cluster the pipeline would run in the Hop process, where the paths of the cluster don't exist. For Databricks, use the cluster type *Databricks*, also for the jobs that the xref:workflow/actions/databricks-job-run.adoc[Databricks job run] action deploys.

[[kubernetes]]
==== Cluster mode on Kubernetes

Hop submits with Spark's own Kubernetes client inside the Hop process and names the driver pod `hop-<id>`. It follows the pod until it ends: `Succeeded` is a successful run, `Failed` or a pod that disappeared is a failure. *Stop* deletes the driver pod, and Kubernetes then removes the executor pods. Hop reaches the API server with the kubeconfig, the service account of its own pod, or the `KUBERNETES_*` environment, the same way `kubectl` does.

What the run configuration needs:

* *Spark master* `k8s://https://<api server>:<port>` and *Deploy mode* Cluster.
* A container image with Spark {spark-version} and Java {java-version}: Spark's own images run Java 17, which cannot load the Hop classes. `docker/integration-tests/spark/Dockerfile.kubernetes` in the Hop source builds one.
* A *Staging folder* the pods download from over a URL they can reach, for example a bucket of an object store in or next to the cluster: *Staging folder* `minio-staging://hop-staging` (a VFS connection) and *Staging folder URL for the cluster* `http://seaweedfs.default.svc.cluster.local:8888/buckets/hop-staging`.
* Rows on the *Spark settings* tab (a key and a value per row) for the image, the service account the driver creates executor pods with, and the volumes the pipelines read and write, for example:
+
[source]
----
spark.kubernetes.container.image=hop-spark-kubernetes:{spark-version}
spark.kubernetes.authenticate.driver.serviceAccountName=spark
spark.executor.instances=2
spark.kubernetes.driver.volumes.persistentVolumeClaim.data.mount.path=/data
spark.kubernetes.driver.volumes.persistentVolumeClaim.data.options.claimName=hop-data
spark.kubernetes.executor.volumes.persistentVolumeClaim.data.mount.path=/data
spark.kubernetes.executor.volumes.persistentVolumeClaim.data.options.claimName=hop-data
----
+
The service account needs to create, watch and delete pods, services and config maps in its namespace, for example through a role binding to the `edit` cluster role. Data in object storage needs no volume.

The id of a run is `<namespace>:<driver pod>`. The driver log is the log of that pod: `kubectl logs <driver pod>`.

==== Generic transform run mode and per-transform override

Most classic Hop transforms (including *Workflow Executor*, *Pipeline Executor*, and mappings) execute on Native Spark as generic `mapPartitions` work. When the input Dataset has many partitions, Spark can run that nested work on multiple executors at once. That is often desirable for pure row transforms, but nested workflows or other non-reentrant side effects may need a single place of execution.

* **Run configuration default** — *Generic transform run mode*: `DISTRIBUTED` (default) or `DRIVER_ONLY`.
* **Per-transform override** — right-click a transform → *Spark Run Mode*:
** *Inherit* — use the run configuration default
** *Force distributed* — always use `mapPartitions` across partitions
** *Force Driver Only* — always run this transform's mini-pipeline on the Spark driver
+
The override is stored on the transform (`attributes` group `spark` / key `run_mode`) and is saved with the pipeline. When a force override is set, a small badge is drawn at the **bottom-left** of the transform icon.

image::pipeline/spark/native-spark-run-mode-force-driver.png[Transform with Force Driver Only Spark run-mode badge,width=70%]

Native Dataset handlers (Spark File / Lake Table, Memory Group By, Sort, Unique, Merge Join) ignore this setting.

[NOTE]
====
`DRIVER_ONLY` collects that transform's input rows on the driver. Prefer `DISTRIBUTED` for high-volume data; use driver-only for nested execution control (for example a Workflow Executor over a modest set of control rows).
====

==== Nested Native Spark pipelines (orchestrator pattern)

A parent Native Spark pipeline can start **child** Native Spark pipelines via **Pipeline Executor** (run configuration = Native Spark):

* Put **Force Driver Only** (or run-config `DRIVER_ONLY`) on the Pipeline Executor so children start on the driver.
* Each child **reuses the parent `SparkSession`** (same Spark application) — it does **not** start a second `spark-submit`.
* Parameterize the child with control keys (country, month, partition) for paths and filters.
* Nested engines **must not stop** the shared session when they finish.

Do **not** run nested Native Spark executors under **DISTRIBUTED** mapPartitions on workers (no safe nested SparkContext). For multi-application isolation (separate Spark apps per key), use an external job launcher instead.

Demo: sample project `spark-demo` pipeline `pipelines/03-run-pipelines.hpl` (see xref:pipeline/spark/cluster-mapping-walkthrough.adoc[Cluster demo walk-through]).

[[transforms-not-supported-on-native-spark]]
=== Transforms not supported on Native Spark

Most classic Hop transforms run on Native Spark via native Dataset handlers or generic `mapPartitions`.
Each transform page says in its *Supported Engines* table whether it runs on Native Spark: *yes* when the integration tests give the same rows as on the Hop engine, *no* when it doesn't work, and *maybe* when no test shows it either way.

For broader design limits (copy/distribute, streaming, Spark SQL, MLlib), see
xref:pipeline/spark/getting-started-with-native-spark.adoc#limitations-and-design-rules[Getting started — Limitations and design rules].

==== Beam-only transforms

==== Refused by the engine

The engine refuses to run a pipeline with one of these transforms, and names the transform and the reason.
Each of them gives wrong rows or no rows when it runs in Spark partitions.

Transforms that need all the rows in one place, or the rows in their original order:

* xref:pipeline/transforms/groupby.adoc[Group By]: use xref:pipeline/transforms/memgroupby.adoc[Memory Group By] (native Spark `groupBy`) instead
* xref:pipeline/transforms/uniquerowsbyhashset.adoc[Unique Rows (HashSet)]: use xref:pipeline/transforms/uniquerows.adoc[Unique Rows] (native Spark `distinct`) or Memory Group By instead
* xref:pipeline/transforms/joinrows.adoc[Join Rows (cartesian product)]: add the same constant field to both inputs and use xref:pipeline/transforms/mergejoin.adoc[Merge Join] on that field instead
* xref:pipeline/transforms/maskfields.adoc[Mask fields]: every partition would keep its own mapping, so the same value would not get the same token
* xref:pipeline/transforms/closure.adoc[Closure generator]
* xref:pipeline/transforms/addfieldschangesequence.adoc[Add value fields changing sequence]: its counter restarts in every partition
* xref:pipeline/transforms/sortedmerge.adoc[Sorted Merge] and xref:pipeline/transforms/sortedschemamerge.adoc[Sorted schema merge]: use xref:pipeline/transforms/sort.adoc[Sort rows] (native Spark sort) on the combined rows instead
* xref:pipeline/transforms/rulesaccumulator.adoc[Rules accumulator]
* xref:pipeline/transforms/analyticquery.adoc[Analytic Query]: LAG and LEAD read the rows before and after in one ordered stream
* xref:pipeline/transforms/append.adoc[Append Streams]: the rows of the head stream come before those of the tail stream
* xref:pipeline/transforms/blockingtransform.adoc[Blocking transform]
* xref:pipeline/transforms/detectemptystream.adoc[Detect Empty Stream]: every partition without rows would report an empty stream
* xref:pipeline/transforms/identifylastrow.adoc[Identify last row in a stream]: every partition would mark its own last row
* xref:pipeline/transforms/mergerows.adoc[Merge rows (diff)]
* xref:pipeline/transforms/multimerge.adoc[Multiway Merge Join]: use xref:pipeline/transforms/mergejoin.adoc[Merge Join] (native Spark join) instead
* xref:pipeline/transforms/repeatfields.adoc[Repeat fields]
* xref:pipeline/transforms/streamschemamerge.adoc[Stream schema merge]: when Spark combines inputs with different layouts, rows go missing

Transforms that work with other transforms of the same Hop pipeline, which a Spark partition doesn't have:

* xref:pipeline/transforms/blockuntiltransformsfinish.adoc[Blocking until transforms finish]
* xref:pipeline/transforms/metainject.adoc[Metadata Injection]
* xref:pipeline/transforms/multi-mapping.adoc[Mapping (multiple inputs/outputs)]
* xref:pipeline/transforms/xmljoin.adoc[XML join]
* xref:pipeline/transforms/pipeline-data-probe.adoc[Pipeline Data Probe]: probes attach to Hop's own pipeline engine only

Transforms that exchange rows, files or variables with the workflow or pipeline executor. A Spark run doesn't pass its previous result to the partitions, its result carries no rows or files, and variables set in a partition don't reach the parent:

* xref:pipeline/transforms/getrowsfromresult.adoc[Get Rows from Result]
* xref:pipeline/transforms/getrecordsfromstream.adoc[Get records from stream]
* xref:pipeline/transforms/filesfromresult.adoc[Files from result]
* xref:pipeline/transforms/copyrowstoresult.adoc[Copy rows to result]
* xref:pipeline/transforms/filestoresult.adoc[Files to result]
* xref:pipeline/transforms/setvariable.adoc[Set Variables]

Other:

* xref:pipeline/transforms/injector.adoc[Injector]: it receives the rows an application hands to Hop's own pipeline engine
* xref:pipeline/transforms/kafkaconsumer.adoc[Kafka consumer]: the engine has no support for unbounded streams; use the Beam Kafka transforms on a Beam engine

==== Limits of the engine

Some transforms work, but not with every kind of value or hop:

* Values of type JSON, UUID, Graph and Vector can't be converted to Spark rows.
* Error hops are not supported, and a transform can only have several outgoing hops when they are target streams (for example the true and false outputs of Filter Rows).
* Transforms of separately installed plugins (Kafka, Mail) can fail to load inside Spark's generated code.

A transform marked *maybe* on its page has no test that shows it works on the native Spark engine, mostly because it needs an outside service.
