= Beam issue triage (umbrella #8708)

[#8708]
== https://github.com/apache/hop/issues/8708[Umbrella: Apache Beam engine, runners and Beam IO issues]

This page tracks the triage of every sub-issue of the umbrella issue
https://github.com/apache/hop/issues/8708[#8708], which groups the open issues related to the Beam
pipeline engine, the four Beam runners (Direct, Flink, Spark and Dataflow) and the Beam IO
transforms.

Each sub-issue gets a decision and an effort rating.
The ratings are *Low* (a few hours), *Medium* (roughly a day) and *High* (more than a day, usually
because the work needs infrastructure that cannot be unit tested).

The work is done in waves, ordered so that each wave leaves the build green on its own.
The status column is ticked off as each wave lands.

|https://github.com/apache/hop/issues/2337[#2337] Beam file output compression

`TextIO.Write.withCompression(Compression)` already exists, and the `Compression` enum covers

Adding a dropdown to the output transform is a small change with no new dependencies.

`GcpOptions.setGcpTempLocation()` exists and `GcpOptions` is already on the plugin classpath.

|Low
|2
|Implement
|Done
|Done in `2f79d7e0b5`.
`BigQueryIO.TypedRead` already has `withQueryLocation(String)` and `withoutValidation()`.
Two new properties on the BigQuery input transform plus two dialog widgets.

|https://github.com/apache/hop/issues/5064[#5064] BigQuery input RECORD (nested) fields
|Low
|2
|Implement
|Done
|Done in `561fb0f217`.
The type derivation did `AvroType.valueOf("RECORD")`, which threw and failed the whole read.
Map `RECORD` to a String and serialise nested values as JSON, which is what the issue asks for.
Changing the output type of a field is release-note material.

|https://github.com/apache/hop/issues/2675[#2675] Kafka Avro with a schema registry
|Medium
|2
|Implement
|Done
|Done in `60cd479791`.
Contains two separate defects.
First, the Confluent serializers are on the compile classpath but `plugins/engines/beam/lib` is
never populated, so the fat jar does not stage them and the Flink task manager fails with a
`ClassNotFoundException`.
Second, the producer throws a bare `NullPointerException` inside `AvroCoder` when the Avro field
carries no schema.
Fix the packaging, and turn the NPE into a clear error message.

|https://github.com/apache/hop/issues/2040[#2040] Apache Beam partitioning support
|Medium
|3
|Implement
|Done
|Added a Beam partition transform wrapping Beam's `Partition`, with a single-partition and a
keyed mode, so the previously unused `SinglePartitionFn` now has a caller and there is a
field-based `KeyedPartitionFn` beside it.
The row count is the assertion that matters: Beam returns one collection per partition and reading
only the first drops the rest, which the end-to-end test verifies by failing with 12 of 100 rows
against the naive version.

|https://github.com/apache/hop/issues/2275[#2275] Beam window by key
|Medium
|3
|Implement
|Done
|Added an optional `keyField` to `BeamWindowMeta`, with a dialog field and docs.
Rows are keyed with `HopKeyFn`, the KV collection is windowed and grouped, and the key is dropped
again so downstream transforms see plain rows; the key is a field already on the row, so it does not
become an extra column.
Note that a GLOBAL window per key and a GLOBAL window overall emit the same row count, so the
end-to-end test proves the keyed branch is reached through the unknown-key-field failure rather than
by row count.

|https://github.com/apache/hop/issues/2357[#2357] Parquet transform and ParquetIO
|Medium
|3
|Implement
|Planned
|`ParquetIO` is not on the plugin classpath: it ships in the separate
`org.apache.beam:beam-sdks-java-io-parquet` artifact.
Adding that one dependency plus a handler covers the Parquet file transforms.

|https://github.com/apache/hop/issues/2358[#2358] Avro transform and AvroIO
|Medium
|3
|Investigate
|Answered
|The issue asks whether a handler is worth the effort. It is, but only for two of the four Avro
transforms, so the work is larger than the original triage assumed.

`HopRowCoder` already handles `GenericRecord`: it writes the schema as JSON alongside the binary
payload and reads it back, which is what the Avro input transform needs, since the schema is only
known once the file has been read.
`HopRowCoderAvroTest` covers that round trip, including a nested record.

The four transforms split in two:

* `AvroEncode` and `AvroDecode` are pure per-row conversions and already work through the generic
handler.
No handler needed.

* `AvroFileInput` and `AvroOutput` cannot work there.
The input is not a source: it reads the filename to open from a field in an incoming row, so on Beam
it has no input collection, the generic handler injects one dummy row, and the transform throws
"Please specify a field to use as the source of data filenames to read".
The output opens one writer and holds it for every row, so every worker would write to the same
file.

Both need a handler built on `AvroIO`, which is already on the classpath.
Note that `hop-tech-avro` is not a dependency of the Beam module, so the meta classes have to be
reached without a compile-time reference, or that dependency has to be added.

NOTE: `AvroIO` moved out of `beam-sdks-java-core` in recent Beam releases; use the
`extensions.avro.io` package.

|https://github.com/apache/hop/issues/2379[#2379] Add Sequence transform handler
|Medium
|3
|Implement
|Done
|Added `BeamAddSequenceTransformHandler` and a stateful `AddSequenceFn`, so the transform no longer
falls through to the generic handler that gave every worker its own sequence.
The counter lives in Beam state and all rows are keyed onto one key, which is what makes it a single
pipeline-wide sequence; a plain field would restart per worker.
The trade-off is that the transform runs at parallelism one, which is inherent to a globally
increasing sequence rather than a shortcut. The database- and counter-backed modes cannot be
expressed on Beam and now fail with an explanation.

|https://github.com/apache/hop/issues/2409[#2409] Beam Debezium IO
|High
|4
|Implement

|https://github.com/apache/hop/issues/3131[#3131] Get the Flink JobID
|Low
|5
|Close with an answer
|Planned
|Not implementable.
Beam 2.74 discards the Flink `JobID`:
`FlinkPipelineExecutionEnvironment.createAttachedPipelineResult()` builds `FlinkRunnerResult` from
`JobExecutionResult` and keeps only the accumulators and the runtime, while the detached variant
`FlinkDetachedRunnerResult` holds its `JobClient` in a private field with no accessor.
There is no supported way to read the `JobID` from `PipelineResult`.
Point people at the Beam job name, which Hop already derives from the pipeline name, and at the
Dataflow equivalent which Hop does report through
`BeamDataFlowPipelineEngine.DETAIL_DATAFLOW_JOB_ID`.

|https://github.com/apache/hop/issues/3478[#3478] Partition and copies on Flink
|Low
|5
|Close with an answer
|Planned
|A question rather than a defect.
On a Beam runner, copies and distribute describe the local Hop engine; the cluster decides its own
parallelism.
Answer using the Flink run configuration parallelism setting, the `SingleThreaded` transform
attribute, and the partitioning work in #2040.

[[open-questions]]
== Open questions

These need an answer before the corresponding wave starts.
They are listed here rather than buried in the table so they are easy to find.

* *#2613 scope.* Does this umbrella include building the Hop-side Elastic transforms, or only the
Beam handler? This roughly doubles the effort of that sub-issue.
* *#2378, #2377 and #2375 licensing.* Snowflake and Splunk pull vendor JDBC drivers with their own
licensing terms. Confirm they belong in the Apache distribution before spending the effort.
* *#2409 unbounded only.* Accept that the Debezium transform can only be a streaming input, or
decline the sub-issue?
* *#2040 user interface.* Should the partitioning controls be disabled on Beam pipelines, where they
are currently ignored, or should the dialogs explain that partitioning is now honoured?
Pick one and apply it consistently.
* *#3131 and #3478.* Is closing a question issue with a detailed answer acceptable, or should the
content become a documentation page instead?
