== Description

The Text File Input transform reads data from a variety of text-file types, including formats generated by spreadsheets and fixed width flat files.

The features of the transform allow you to read from a list of files or directories, use wild cards in the form of regular expressions, and accept generalized filenames from previous transforms.

**Selecting files using Regular Expressions**

The Text File Input transform can search for files by wildcard in the form of a regular expression.
Regular expressions are more sophisticated than using '*' and '?' wildcards.
Below are a few examples of regular expressions:

[options="header"]
|===
|Filename|Regular Expression|Files selected
|/dirA/|.userdata.\.txt|Find all files in /dirA/ with names containing userdata and ending with .txt
|/dirB/|AAA.*|Find all files in /dirB/ with names that start with AAA
|/dirC/|[ENG:A-Z][ENG:0-9].*|Find all files in /dirC/ with names that start with a capital and followed by a digit (A0-Z9)

This option allows you to construct your filename in another transform, such as "Get Filenames", and then pass it to this transform, either as a field in the input stream or reading directly from the other transform's output.
This lets you use file names from any source, including text files and database tables.

=== Performance Tab

The performance tab sets how the copies of this transform share the work, and how files on remote storage are downloaded.

[NOTE]
====
Normally, each copy of this transform does all of its work on a single thread.
These settings can start additional threads:

* *Read-ahead blocks* above 0: blocks of the file are downloaded on background threads while the rows are being read. See <<read-ahead>>.
* *Running in parallel?* combined with *Allow breaks in enclosed fields?*: before any rows are read, the large files are scanned using one extra thread per copy.
====

[options="header"]
|===
|Option|Description
|Running in parallel?|Share the files between the copies of this transform instead of every copy reading every file. Large files are cut into chunks and each copy reads the next chunk not yet taken. See <<running-in-parallel>>.
|Chunk size|The largest piece of a file one copy reads when running in parallel, for example 64MB or 1GB. Leave it empty for 128MB. With little data the pieces are smaller, so that every copy gets work.
|Read-ahead blocks|For files on remote storage such as S3, Azure or Google Cloud Storage: how many blocks of a file are downloaded at the same time, each over its own connection, while its rows are read. [[running-in-parallel]]
==== Running in parallel

Running this transform in several copies with *Running in parallel?* enabled spreads the work over the copies: every line is read by exactly one copy.
Set the number of copies on the transform in the pipeline (right-click the transform, *Number of copies*).
With one copy, *Running in parallel?* has no effect.

===== How the work is shared

Before the copies read anything, the files are divided into pieces called chunks: a small file is one chunk, a large file is cut into several.
The copies share one list of chunks. Each copy takes the next chunk nobody has taken yet, reads it, and takes the next, until none are left.
A fast copy therefore reads more chunks than a slow one, and a copy can read pieces of several files.

A line belongs to the chunk that holds its first byte. The copy reading that chunk reads the whole line, even when it runs past the end of the chunk, and the copy reading the next chunk skips it.
That way no line is lost or read twice where a file is cut.

===== When a file is cut into chunks

All files are compared to one *split size*, worked out from the total size of all files to read:

----
split size = smallest of ( chunk size , largest of ( 4 MB , total size / number of copies ) )
----

* A file no larger than the split size is read whole, by one copy.
* A larger file is cut into chunks of the split size.
* The chunk size is 128 MB when left empty.

So a file is never cut just because there are several copies:

* With the default chunk size, files of 4 MB or less are always read whole: cutting them would cost more than it saves.
* When there is enough data to give every copy a full share without cutting, no file is cut either. Many medium-sized files are simply divided over the copies.
* With little data the split size is smaller than the chunk size, so that every copy still gets work.
* A chunk size below 4 MB, such as `1KB`, is used as it is, without the 4 MB minimum. That is mostly useful for testing.
* On storage that reads in blocks of its own, a chunk is never smaller than that read block size, such as the *Read block size* of an Azure or S3 connection: a smaller chunk would still download whole blocks. A chunk size set below it is not an error: the transform logs a warning and uses the block size.

Some examples, with the default chunk size of 128 MB:

[options="header"]
|===
|Files|Copies|Split size|Result
|1 file of 3 MB|4|4 MB|The file is read whole by one copy.
|1 file of 10 MB|4|4 MB|3 chunks: 4 MB, 4 MB and 2 MB.
|10 files of 10 MB|4|25 MB|No file is cut; the copies share the 10 files.
|1 file of 1 GB|8|128 MB|8 chunks of 128 MB.
|1 file of 1 GB and 100 files of 1 MB|4|128 MB|The large file is cut into 8 chunks; the small files are read whole.
|===

Even when it is larger than the split size, a file is read whole by one copy, with a line in the log saying why, when:

* its storage can't start reading in the middle of a file. Local files, S3, Google Cloud Storage, Azure, SFTP, SMB and HTTP can be read in chunks.
* its encoding has no line feed that can be found by its bytes, such as UTF-32 or EBCDIC.
* its header lines take up more than the first 1 MB of the file.

[[read-ahead]]
===== Reading from remote storage

On object storage such as S3, Azure and Google Cloud Storage one connection is often limited to a few MB/s, however fast the network is.
A plain read also downloads the next part of a file only once the rows before it are processed, so the network waits for the processing and the other way around.

With *Read-ahead blocks* set to 1 or more, this transform downloads a file from remote storage in blocks, several at a time, each over its own connection, while it processes the rows of the blocks already there.
*Read-ahead blocks* sets how many blocks are downloaded at the same time for each file or chunk being read.
It is 0 by default: every copy of this transform then does all its work, reading included, on its own thread, as it always did.
With 1 or more blocks the downloads run on extra threads besides the copy's: up to that many per file or chunk being read, so copies × blocks in total. Try 4 for a large file on remote storage.
The size of a block belongs to the storage, not to this transform: it is the *Read block size* of the xref:metadata-types/azure-authentication.adoc[Azure connection], the xref:vfs/aws-s3-vfs.adoc#_read_block_size[S3 connection] or the xref:vfs/google-cloud-storage-vfs.adoc#_read_block_size[Google Cloud Storage options], and 8 MB for other storage.
Where the storage supports it, every block is downloaded with one request for exactly its bytes.

* This works for every file system that can start reading in the middle of a file, also without *Running in parallel?*. Local files are always read directly: the operating system reads ahead itself.
* Running in parallel, a copy fetches ahead up to the end of its chunk only. The rest of the last line, which runs past the end, is fetched when it is reached.
* With 10 copies and 4 read-ahead blocks, up to 40 downloads run at the same time.
* Every copy holds up to *Read-ahead blocks* × the block size in memory: 32 MB with the defaults, so 320 MB for 10 copies. Lower the number of blocks, or the read block size of the connection, when memory is short.
* More blocks help as long as the network has room for more connections. When the processing can't keep up any more, more copies help instead.
* A block whose download fails is downloaded again, up to 3 times in all, after waiting 1 and then 2 seconds; every retry is logged. A block that still fails stops the read with an error, and the transform fails: no rows are made from the part of a line read before the error, and the file is never read on past the failed block.

===== Headers, rows and limits

* The header lines are skipped once per file, by the copy that reads its start. Chunks further on in the file start after the header.
* The rows come out in no particular order. If the order matters, sort the rows afterwards or run one copy.
* The row number and the *Limit* count per copy.
* A file is added to the result, and reported to lineage, once, not once per chunk.
* With *Allow breaks in enclosed fields?* enabled, a line feed inside an enclosed field doesn't start a new row, so a chunk can't simply start after any line feed. The large files are then first read once more, on one extra thread per copy while the copies wait, to find where each chunk's first row starts, and the chunks are cut exactly there. This works in UTF-8, ISO-8859, windows-125x and UTF-16, with an enclosure and escape character in plain ASCII; other files are read whole by one copy.

===== Filenames from a previous transform

With *Accept filenames from previous transforms* enabled, the previous transform spreads its filename rows over the copies, so each copy receives only part of the filenames.
With *Running in parallel?* enabled the copies first collect all filenames, from all copies, and then divide all these files into chunks together, following the rules above. The files are read the same way as files from the file list.

* Every copy first reads all its filename rows, as it does without parallel reading, so collecting them doesn't delay reading.
* The previous transform must have finished sending filenames before the copies start reading.
* With *Pass through fields from previous transform* enabled, every row read from a file carries the fields of the row that named that file. This is also true for a chunk read by another copy, and for a copy that received no filename rows itself.
* A file named in two rows is read twice, once for each row, as it is without parallel reading.
* If the previous transform copies its rows to every copy instead of distributing them, every copy receives every filename. Each file is then still read once, not once per copy.
* A file that doesn't exist is handled by the copy that tries to open it, following the error handling settings, as without parallel reading.

===== Settings that can't be combined

Reading in parallel can't be combined with settings that need each file read from its first line by one copy:

* wrapped lines
* paged layout
* a footer
* row numbers by file
* compression
* *Stop on filter*
* repeated fields

The dialog doesn't let you switch on both. A pipeline that combines them anyway, for example through metadata injection, doesn't start.

===== Several copies without running in parallel

Running this transform in several copies without *Running in parallel?* is refused, because every copy would read every file and output every row once per copy.

The exception is filenames from a previous transform: the filenames are already divided over the copies, so each copy reads the files it receives, whole.
Turn on *Running in parallel?* to also cut large files into chunks.
