== Description

The Update transform looks up a row in a table using one or more lookup keys and updates it if needed.

If the row can't be found, nothing is done.

If the row is found the row in the table is updated.

== Options

[options="header"]
|===
|Option|Description
|Commit size|The number of rows to update before running a commit.
|Use batch updates?|Allows the use of batch updates.
|Skip lookup|Skips the row lookup.
|Ignore lookup failure?|Allows the transform to skip lookup failures.
|Flag field (key found)|Field which contains whether the key was found or not.
|Connection|The database connection to which data is written.
|Key Lookup table|Allows you to specify a list of field values and comparators.
You can use the following comparators: =, = ~NULL, <>, <, <=, >, >=, LIKE, BETWEEN, IS NULL, IS NOT NULL
|SQL button|Click SQL to generate the SQL to create the table and indexes for correct operation.
|Transform name|Name of the transform; this name has to be unique in a single pipeline.
|Target schema|The name of the Schema for the table to which data is written.
This is important for data sources that allow for table names with periods in them.
|Target table|Name of the table in which you want to do the update.
|Update Fields|Allows you to specify all fields in the table you want to update.
|===

== Commits and when rows are passed on

When the rows are updated one by one (*Use batch updates?* off, or batching switched off, see below), a row leaves the transform only after the commit that includes its update.
The rows that came in after it wait as well, also the rows that needed no update, whose key was not found or that failed, so the rows keep their input order on the main output and the error hop.
The transform commits when a commit size of rows waits; the rows that needed no update count towards it, so at most a commit size of rows waits in memory.
When the transform fails or is stopped, the updates of the rows that still wait are rolled back and those rows are not passed on; the log says how many.
So a row that appears on the main output is in the table.

On some databases a failed statement loses the work of the whole open transaction, and there is no savepoint to undo only the failed row: DuckDB is one.
On such a database, when its driver's behaviour has been measured (see below), a failed row with an error hop rolls the transaction back, the updates of the rows that wait for the commit are run again, and only the failed row goes to the error hop.
A row whose update fails when it runs again goes to the error hop as well.
Because those updates are sent to the database a second time, a failed row can fire non-transactional triggers again.
With *As before* on the connection or `HOP_DATABASE_BATCH_RECOVERY` set to `LEGACY`, nothing is run again: on DuckDB a failed row then loses the updates of the rows in front of it since the last commit, although those rows are passed on, and every row after it fails as well.

A row is passed on right after its update, as before, when:

* the commit size is 0: every update is committed at once,
* the pipeline is transactional: the connection is shared and only committed at the end of the pipeline, so holding the rows back would hold up the transforms after this one until then,
* the variable `HOP_DATABASE_BATCH_RECOVERY` is set to `LEGACY`.

== Batches and error handling

With *Use batch updates?* on, the updates are sent to the database in batches of the commit size.
When the update of a row in a batch fails, what happened to the other rows of the batch depends on the database's JDBC driver: some run the other rows, some stop at the failing row, and some lose the whole batch.

On a database whose driver's behaviour has been measured, the transform uses it to work out which rows of a failed batch are in the database, and with an error hop attached it sends each row to exactly one stream: the main output for rows that were updated, the error hop for rows that were refused.
A row only appears on the main output after the database has committed its update, and the rows keep their input order, also the rows that needed no update and the rows whose key was not found.
On such a database the transform also keeps batching when an error hop is attached.
That includes PostgreSQL, where an error hop otherwise switches batching off and every row runs on its own behind a savepoint.
Without an error hop a failed batch is rolled back and the transform stops, as before.
When the transform is stopped or fails, the rows that still wait in its batch are not updated.

The databases measured so far, with their default connection options, are listed in the development manual under "Creating a dialect".
On every other database, and when a connection option changes how the driver handles a failed batch, the transform handles a failed batch as it always did.

To go back to that behaviour on a measured database:

* set *When a batch fails, the driver* on the *Advanced* tab of the connection to *As before*, or
* set the variable `HOP_DATABASE_BATCH_RECOVERY` to `LEGACY`, for every connection.

The same option can name what the driver does, for a connection whose options change it.

When a failed batch is worked out this way, the update of a row can be sent to the database more than once, so a failed batch can fire non-transactional triggers again.
