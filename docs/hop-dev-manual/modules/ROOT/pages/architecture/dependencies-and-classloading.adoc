= Dependencies and classloading

Hop loads plugins from folders at runtime, which means dependency management is not only a Maven concern: where a jar lands decides which classloader sees it, and that decides whether your plugin works.

== Managing Hop dependency versions

Import `org.apache.hop:hop-bom` in your project's `dependencyManagement` to align Hop artifact versions.
Set the `hop.version` property to the Hop version you use.

[source,xml]
----
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>org.apache.hop</groupId>
      <artifactId>hop-bom</artifactId>
      <version>${hop.version}</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>
----

Then declare the dependencies you need without individual versions, including `hop-core`, `hop-engine`, and `hop-transform-*` artifacts such as `hop-transform-calculator`.
For a plugin running inside Hop, use `provided` scope for Hop dependencies supplied by the host rather than bundling another copy.

[source,xml]
----
<dependencies>
  <dependency>
    <groupId>org.apache.hop</groupId>
    <artifactId>hop-core</artifactId>
    <scope>provided</scope>
  </dependency>
  <dependency>
    <groupId>org.apache.hop</groupId>
    <artifactId>hop-engine</artifactId>
    <scope>provided</scope>
  </dependency>
  <dependency>
    <groupId>org.apache.hop</groupId>
    <artifactId>hop-transform-calculator</artifactId>
    <scope>provided</scope>
  </dependency>
</dependencies>
----

The BOM manages JAR libraries from the `base` reactor, including plugin JARs, without requiring consumers to activate a profile.
POM artifacts, distribution ZIPs such as `hop-client`, and modules from build/test tooling profiles such as `config-doc` are not managed.
Sources, Javadoc and test classifiers are not managed.
The BOM manages versions; importing it does not add dependencies, package jars, or change runtime classloading or plugin visibility.
Declaring a dependency on another plugin does not by itself make that plugin's classes visible at runtime.
`hop-libs` provides separate third-party dependency management and is not imported by `hop-bom`.
See xref:build-and-test.adoc[Building and testing] for BOM maintenance and validation.

== The layout

`lib/core`::
Shared by everything. One classloader, the parent of all plugin classloaders.

`lib/jdbc`::
JDBC drivers, kept apart because most of them cannot ship with Hop for licensing reasons. `DatabasePluginType` adds this folder as an extra library folder; `HOP_SHARED_JDBC_FOLDERS` can change it.

`plugins/<category>/<plugin>/`::
The plugin jar, with its private dependencies in a `lib/` subfolder next to it.

Each plugin gets its own `URLClassLoader` over its own jar and its `lib/`, with the Hop classloader as parent — so a plugin sees `lib/core`, but `lib/core` never sees a plugin.

== How Maven scope decides placement

The shared assembly component `assemblies/shared/hop-plugin-libs.xml` routes by scope:

[cols="1,3", options="header"]
|===
|Scope |Where it lands

|`provided`
|`lib/core`, unless it is Hop itself, SWT, SLF4J or another artifact on the shared exclude list.

|`runtime` / `compile`
|The plugin's own `lib/` folder.

|`test` (JDBC drivers)
|`lib/jdbc`, for the drivers a plugin declares.
|===

This is why the scope you pick in a plugin pom is a packaging decision, not just a compilation one.

== Two rules

Never ship a jar that is already in `lib/core`::
The plugin classloader would find the parent's copy anyway, so the second copy is dead weight at best.
At worst the two versions differ and behaviour depends on which classloader asked.
`tools/find_duplicate_jars.sh` finds these.

`tools/check-assembly-jar-versions.py` reads the client assembly zip and reports a library that landed in more than one version.
Two versions in `lib/core` share a classloader, so which one loads depends on classpath order.
A plugin that ships a different version loads that copy for itself, because the plugin classloader looks at its own jars first, while the rest of Hop still sees `lib/core`.

Plugins that must see each other's classes share a `classLoaderGroup`::
A database dialect and its bulk loader, a VFS provider and its metadata type, an SFTP connection and the actions using it.
Without it, an object created by one classloader will not cast to the class the other one knows — the failure looks like an impossible `ClassCastException` between two identically named classes.

== Size

`tools/check-assembly-size.sh` runs in CI and fails the build when the packages get too large; ASF Artifactory rejects uploads over roughly 850 MB.
Adding a heavy dependency to a widely-used module is a distribution-wide cost.
