[[Architecture-ExtensionPoints]]
= Extension points and when they fire

An extension point is a named moment at which Hop calls every plugin listening for it.
How to write such a plugin is on the xref:plugin-types/execution-observability.adoc#_extension_point[Execution and observability] page.
This page is about the moments themselves: when each one fires, in which order, on which engine, and what it hands over.

The names are the constants of two enums:

* `HopExtensionPoint` in `org.apache.hop.core.extension` (core): runs, files, metadata, the command line tools and most of Hop GUI.
* `HopGuiExtensionPoint` in `org.apache.hop.ui.hopgui` (ui): file dialogs, the explorer and a few Hop GUI updates.

A listener names the moment in `extensionPointId`; the generic type of `IExtensionPoint<T>` is the object Hop hands over.
Extension points run on the thread that fires them, one listener after the other, so a slow listener slows down the run.

== A pipeline run on the local engine

The local engine (`Pipeline`, `LocalPipelineEngine`) fires the full set, in this order:

[cols="1,2,3",options="header"]
|===
|Extension point |Object |When

|`PipelinePrepareExecution`
|`IPipelineEngine`
|`prepareExecution()` has checked the pipeline against the engine (engine compatibility), and is about to activate the parameters, create the row sets and the transform copies.

|`TransformBeforeInitialize`
|`TransformInitThread`
|For every transform copy, right before its `init()` starts on an init thread of its own.

|`TransformAfterInitialize`
|`TransformInitThread`
|For every transform copy, once its init thread is done. All copies initialize at the same time, so the order between copies is not fixed.

|`TransformFailed`
|`ExecutionFailure`
|A transform copy failed to initialize. The pipeline does not start.

|`PipelineStartThreads`
|`IPipelineEngine`
|`startThreads()` begins: before the execution started listeners and before any transform thread starts.

|`TransformBeforeStart`
|`TransformMetaDataCombi`
|For every transform copy, right before its thread starts.

|`PipelineStart`
|`IPipelineEngine`
|All transform threads were started. Rows may already be flowing.

|`TransformFinished`
|`TransformMetaDataCombi`
|A transform copy finished. Fired from the copy's finished listener, ahead of the pipeline's own detection of the end of the run.

|`TransformFailed`
|`ExecutionFailure`
|A transform copy failed while processing rows: it threw an exception, or it finished with errors.

|`PipelineFinish`
|`IPipelineEngine`
|The last transform copy finished. This is the first execution finished listener: the others run after it.

|`PipelineFailed`
|`ExecutionFailure`
|The run failed: after all execution finished listeners, before `PipelineCompleted`.

|`PipelineCompleted`
|`IPipelineEngine`
|Everything is done: the result, the status and the failures are final. `waitUntilFinished()` returns after this, so a caller such as `hop-run` can leave the JVM straight after it: work that has to happen at the end of a run, such as flushing lineage, belongs here.
|===

`PipelineMetaLoaded` fires earlier, whenever a `PipelineMeta` is read from a file, also when nothing runs it.

The single-threaded pipeline type runs the transforms one at a time in an executor, without threads of their own.
It fires the same extension points; `TransformBeforeStart` comes for every copy before `PipelineStart`, and `TransformFinished` when the executor disposes the copies at the end of the run.

== Which engine fires what

[cols="2,1,1,1,1",options="header"]
|===
|Extension point |Local |Remote (Hop Server) |Beam |Native Spark

|`PipelinePrepareExecution` |yes |no |yes |yes
|`PipelineStartThreads` |yes |no |yes |yes
|`PipelineStart` |yes |yes |yes |yes
|`PipelineFinish` |yes |yes |yes |yes
|`PipelineCompleted` |yes |yes |yes |yes
|`PipelineFailed` |yes |no |no |no
|`TransformBeforeInitialize`, `TransformAfterInitialize`, `TransformBeforeStart`, `TransformFinished`, `TransformFailed` |yes |no |no |no
|===

The *remote* engine sends the pipeline to a Hop Server.
The server runs it on its own local engine, which fires the full set in the server's JVM; the client only sees the start and the end.

The *Beam* and *native Spark* engines fire the pipeline-level points at the same moments as the local engine, once per run, but no transform-level points: a transform there is a step in a Beam or Spark job, not a copy with a thread.

[IMPORTANT]
====
Beam and native Spark run a Hop transform without a native implementation inside a small local pipeline: on Beam one per transform and worker, on native Spark one per transform and partition.
These are local engines of the single-threaded type, and they fire the local engine's extension points, pipeline and transform level, for every bundle or partition they run.
A listener that only wants the run itself sees these too.
They have no dedicated marker yet: their pipeline is named after the transform, their run configuration is named `beam-transform-local (...)` or `spark-transform-local (...)`, and their type is `SingleThreaded`.
====

== A workflow run on the local engine

The local workflow engine (`Workflow`, `LocalWorkflowEngine`) fires:

[cols="1,2,3",options="header"]
|===
|Extension point |Object |When

|`WorkflowStart`
|`IWorkflowEngine`
|The workflow has checked its actions against the engine (engine compatibility), after the execution started listeners, before the first action.

|`WorkflowBeginProcessing`
|`WorkflowExecutionExtension`
|Right after `WorkflowStart`: the start of processing.

|`WorkflowBeforeActionExecution`
|`WorkflowExecutionExtension`
|Before every action. A listener can stop the action from running: set `executeAction` to false.

|`ActionFailed`
|`ExecutionFailure`
|The action threw an exception, raised its error count, or ran a child pipeline or workflow that failed.

|`WorkflowAfterActionExecution`
|`WorkflowExecutionExtension`
|After every action, with its result.

|`WorkflowFailed`
|`ExecutionFailure`
|The workflow ended with a false result, unless someone stopped it and nothing went wrong.

|`WorkflowFinish`
|`IWorkflowEngine`
|The workflow ended, successfully or not. The execution finished listeners run after it.
|===

`WorkflowMetaLoaded` fires whenever a `WorkflowMeta` is read from a file.

The remote workflow engine fires none of these on the client: the Hop Server runs the workflow on its local engine, which fires them there.

[NOTE]
====
A child workflow that a Workflow action runs fires `WorkflowFinish` twice: once at the end of its own run, and once more from the thread the action runs it on (`ActionWorkflowRunner`).
A listener on `WorkflowFinish` should not assume it is called once per run.
====

== Before and around a run

[cols="1,3",options="header"]
|===
|Extension point |When

|`HopRunCalculateFilename`
|`hop-run` has worked out the file to run, before it uses it.

|`HopRunStart`
|`hop-run` starts, before it loads the metadata and runs the file.

|`HopRunEnd`
|`hop-run` is done.

|`HopGuiPipelineMetaExecutionStart`
|Hop GUI starts to run a pipeline (`PipelineMeta`).

|`HopGuiPipelineExecutionConfiguration`
|Right before Hop GUI shows the run configuration of a pipeline.

|`HopGuiPipelineBeforeStart`
|Right before Hop GUI starts the pipeline engine.

|`HopGuiWorkflowMetaExecutionStart`, `HopGuiWorkflowExecutionConfiguration`, `HopGuiWorkflowBeforeStart`
|The same for a workflow. `HopGuiWorkflowBeforeStart` also fires in `hop-run`.

|`HopGuiRunConfiguration`
|A dialog that picks a run configuration (run options, Pipeline and Workflow actions, Pipeline and Workflow executor, Metadata injection) fills its list: the extension point gets the list, so a plugin can add to it.

|`HopGuiPipelineFinished` (`HopGuiExtensionPoint`)
|A pipeline that Hop GUI ran has finished.
|===

== The import tool

`HopImportStart` and `HopImportEnd` fire at the start and the end of `hop-import`.
In between, `HopImportTargetMetadataReady` fires once the metadata of the target exists, `HopImportRewriteMetadata` once the imported files and connections are written, and `HopImportCreateProject` to register a project for the target folder.

== Declared but not fired

These constants exist, and some have listeners, but nothing in Hop fires them at the moment.
A plugin that listens to one of them is never called:

`HopGuiEnd`, `OpenRecent`, `PipelineHeartbeat`, `PipelineBeforeClose`, `PipelineAfterClose`, `PipelineChanged`, `PipelineTransformRightClick`, `RunConfigurationSelection`, `RunConfigurationIsRemote`, `WorkflowBeforeOpen`, `WorkflowBeforeClose`, `WorkflowAfterClose`, `WorkflowChanged`, `WorkflowDialogShowRetrieveLogTableFields`, `HopGuiPipelineAfterClose`, `HopGuiWorkflowAfterClose`, and in `HopGuiExtensionPoint` `HopGuiFileSaveDialog` and `HopGuiNewPipelineTab`.

== Firing your own

Anything can fire an extension point, by name:

[source,java]
----
ExtensionPointHandler.callExtensionPoint(
    log, variables, HopExtensionPoint.PipelineStart.id, pipeline);
----

A plugin may define a name of its own and fire it; listeners find it by that name.
When an engine fires the run's extension points, it should fire them at the moments in the tables above, each once per run, with the same object type: listeners rely on that order, and on `PipelineCompleted` being the last call before `waitUntilFinished()` returns.
