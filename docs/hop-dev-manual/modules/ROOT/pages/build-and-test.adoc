[[BuildAndTest]]
= Building and testing

== What you need

* A JDK {java-version}. The build targets Java {java-version} and the tests are skipped on anything older.
* Maven 3.6.3 or newer — or nothing at all, and use the bundled wrapper `./mvnw`.

[source,bash]
----
./mvnw clean install
----

That builds every module, runs the unit tests, applies the license and formatting checks, and produces the distributions under `assemblies/`.

== Useful invocations

[cols="2,3", options="header"]
|===
|Command |What it does

|`./mvnw clean install`
|The full build.

|`./mvnw clean install -Pfast-build`
|Skips tests, Spotless, RAT, Javadoc and coverage. For a quick compile, never for a build you intend to trust.

|`./mvnw clean install -Dassemblies=false`
|Builds the code but not the distributions. Much faster when you are only changing Java.

|`./mvnw clean install -pl plugins/transforms/foo -am`
|One module and what it depends on.

|`./mvnw spotless:apply`
|Reformats the code. Run this before committing.

|`./mvnw test -pl core`
|Unit tests of a single module.

|`./mvnw -pl bom test`
|Runs the BOM maintenance tests.

|`./mvnw apache-rat:check -Drat.skip=false`
|Runs the Apache RAT license check explicitly.
|===

== Profiles

Several profiles activate themselves, which is why the build usually needs no flags:

`base` / `assemblies` / `web-tests`::
Decide which module sets are in the reactor. All are on unless you pass `-Dbase=false`, `-Dassemblies=false` or `-Dweb-tests=false`.

`swt-unix` / `swt-mac` / `swt-windows`::
Selected by your operating system, and pick the matching SWT artifact. `swt-mac` also adds `-XstartOnFirstThread` to the test JVM, which SWT needs on macOS.

`assembly`::
Activates for any module that has a `src/assembly` folder, and packages it as a zip. This is why a plugin needs no assembly configuration in its pom.

`filtered-resources`::
Activates for any module with a `src/main/resources-filtered` folder.

And the opt-in ones:

`fast-build`::
Skips every check and every test.

`uitest` / `skip-uitest`::
Run only, or skip, the SWTBot UI tests. See xref:testing/ui-testing.adoc[UI tests with SWTBot].

`webtest`::
The Selenium tests that drive Hop Web in a container. The `web-tests` module is always in the reactor, so version changes and releases update it, but its tests are skipped unless you ask for them: they need Docker and take minutes. Run them with `mvn -Dwebtest -pl web-tests test`.

`apache-release` / `deploy-snapshots`::
Release plumbing, including the CycloneDX SBOM. See xref:apache-release/index.adoc[the release process].

== Building behind a firewall

Maven dependencies and plugins go through the `<mirror>` in your `settings.xml`.
Besides Maven Central, a few modules declare their own repositories (Clojars, Confluent, Splunk, JetBrains), so your repository manager has to proxy those too.

Four files are not Maven artifacts and are downloaded directly, ignoring `<mirror>`:

[cols="2,3", options="header"]
|===
|Property |Default

|`swtbot.plugins.url`
|`\https://download.eclipse.org/technology/swtbot/releases/${swtbot.version}/plugins` (two jars)

|`tm4e.core.download.url`
|`\https://download.eclipse.org/tm4e/releases/${tm4e.core.version}/plugins/${tm4e.core.download.file}`

|`monaco.download.url`
|`\https://registry.npmjs.org/monaco-editor/-/monaco-editor-${monaco.version}.tgz`
|===

To fetch them from a repository manager, set these properties in a profile in your `settings.xml`.
`download.auth.serverId` names the `<server>` whose credentials are used for all four downloads.
Keep the `${...}` placeholders: Maven fills them in, so the profile keeps working when Hop updates these versions.

[source,xml]
----
<settings>
  <servers>
    <server>
      <id>artifactory</id>
      <username>...</username>
      <password>...</password>
    </server>
  </servers>
  <profiles>
    <profile>
      <id>hop-downloads</id>
      <properties>
        <download.auth.serverId>artifactory</download.auth.serverId>
        <swtbot.plugins.url>https://artifactory.example.com/eclipse/technology/swtbot/releases/${swtbot.version}/plugins</swtbot.plugins.url>
        <tm4e.core.download.url>https://artifactory.example.com/eclipse/tm4e/releases/${tm4e.core.version}/plugins/${tm4e.core.download.file}</tm4e.core.download.url>
        <monaco.download.url>https://artifactory.example.com/api/npm/npm/monaco-editor/-/monaco-editor-${monaco.version}.tgz</monaco.download.url>
      </properties>
    </profile>
  </profiles>
  <activeProfiles>
    <activeProfile>hop-downloads</activeProfile>
  </activeProfiles>
</settings>
----

The same properties also work as `-D` options on the command line.

== Checks that must pass

Formatting — Spotless::
Java is formatted with google-java-format, imports are ordered and unused ones removed, and `pom.xml` files are sorted.
Run `./mvnw spotless:apply` before you commit; CI runs `spotless:check` and fails on any difference.

License headers — Apache RAT::
Every source and text file needs the Apache License 2.0 header, including new `.adoc` pages.
RAT fails the build otherwise.
See xref:setup-dev-environment.adoc[Setting up your development environment] for configuring your IDE to add it automatically.

Annotation index — Jandex::
Bound for every module, so plugin discovery works. Nothing to do unless you are building a plugin outside this repository.

Tests::
JUnit 5 through Surefire. UI tests are tagged and can be included or excluded, see below.

== Maintaining the Hop BOM

The `bom` module publishes the `org.apache.hop:hop-bom` POM for consumers to import into `dependencyManagement`.
See xref:architecture/dependencies-and-classloading.adoc[Dependencies and classloading] for the import and versionless dependency examples.
The module uses `jar` packaging so the normal Maven test lifecycle runs its JUnit maintenance tests.
The main JAR contains the build-time `BomGenerator` tool and license resources; consumers import the POM, not the JAR.
Producing this main JAR allows normal Maven installation and deployment without publishing a test JAR or allowing incomplete projects.
Jandex indexing is disabled because the generator is not a Hop runtime plugin.

The checked-in `bom/pom.xml` is generated in full by `bom/src/main/java/org/apache/hop/bom/BomGenerator.java`; do not edit it manually.
The generator extracts the release version from the root POM and recursively follows direct module declarations and the `base` profile's module declarations, independently of the active reactor.
Undeclared directories, including nested worktrees and standalone tools, are not scanned, so discovery does not depend on Git ignore rules or local Git configuration.
Only JAR libraries are managed, unconditionally in the top-level dependency management; the BOM does not require consumers to activate the `base` profile.
Other module profiles, including `config-doc`, `assemblies`, and `webtest`, are ignored, and POM and ZIP artifacts are not managed.
The generator validates library release alignment, duplicate coordinates, and exclusions before writing the complete POM.
The maintenance test generates a POM in a temporary directory and compares its exact content with the checked-in file.
Normal builds do not regenerate the source POM; they fail if it is out of date.
When adding, removing, or changing a published module, regenerate the BOM and keep these checks passing.
Keep exclusions narrow: the BOM itself and unpublished build/test artifacts.
The exact exclusions and their reasons are recorded in `BomGenerator`.
They cover the BOM itself and unpublished local Eclipse wrappers.
The BOM is forced into incremental builds so adding or removing another module also runs its coverage check.
Do not use broad exclusions to hide missing published artifacts.

Run the generator from the project root with Java 21 or later; source-file launch needs no previously built Hop artifacts:

[source,bash]
----
java bom/src/main/java/org/apache/hop/bom/BomGenerator.java
----

The first optional argument is the project root and the second is the output POM path.
Without a root argument, the generator checks the working directory and at most one parent for both `mvnw` and `Jenkinsfile`.
Without an output argument, it writes `<root>/bom/pom.xml`.
For example, generate a separate file for inspection with:

[source,bash]
----
java bom/src/main/java/org/apache/hop/bom/BomGenerator.java . /tmp/hop-bom.xml
----

During publication, `flatten-maven-plugin` writes a consumer POM under `bom/target` and Maven installs or deploys that file instead of the source POM.
It removes the parent, profiles, build configuration, properties, and inherited dependencies while preserving the BOM's own unconditional dependency management, so importing it does not impose the root POM's third-party versions.

Run the maintenance tests and license check with:

[source,bash]
----
./mvnw -pl bom test
./mvnw apache-rat:check -Drat.skip=false
----

== What CI runs

`Jenkinsfile`::
The per-change build: full `clean deploy` under `xvfb-run` so the UI tests have a display, an assembly size check (`tools/check-assembly-size.sh` — ASF Artifactory rejects packages over roughly 850 MB), then the Docker images and the snapshot deploy.

`Jenkinsfile.daily`::
Build and test plus a code quality stage, and the integration tests against the built image.

`Jenkinsfile.hop-web-selenium`::
The Hop Web Selenium suite.

CI builds with `-fae` and `-Dsurefire.rerunFailingTestsCount=2`, so a flaky test can pass on CI and still be a real problem.
